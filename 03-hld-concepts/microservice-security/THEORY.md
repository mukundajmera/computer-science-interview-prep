# Microservice Security & Zero Trust

## Paradigm Shift: Perimeter Security vs Zero Trust

Historically, networks relied on **Perimeter Security** (the "Castle and Moat" model). Once inside the corporate network (the castle), users and applications were inherently trusted. 

**Zero Trust** architecture flips this paradigm: "Never trust, always verify." 
- It assumes the network is hostile and compromised.
- Trust is never granted implicitly based on network location.
- Every request is authenticated, authorized, and encrypted, regardless of whether it originates from inside or outside the network.

## OAuth 2.0 & OIDC Modern Flows

### Authorization Code with PKCE

Proof Key for Code Exchange (PKCE) is the recommended authorization flow, especially for single-page and mobile apps, avoiding the need to store a client secret.

1. **Code Verifier**: A cryptographically random string generated by the client.
2. **Code Challenge**: The client hashes the verifier using SHA-256 and base64url-encodes the result.
3. The client sends the `code_challenge` to the authorization server during the login request.
4. After user login, the client receives an authorization code.
5. To exchange the code for tokens, the client sends the authorization code and the original `code_verifier`.
6. The authorization server hashes the `code_verifier` and compares it to the previously stored `code_challenge`. If they match, tokens are issued.

### Client Credentials for M2M

Used for Machine-to-Machine (M2M) communication where no user is involved. Microservice A authenticates with the Authorization Server using its `client_id` and `client_secret` to obtain an Access Token to call Microservice B.

### Refresh Token Rotation

To minimize the risk of compromised refresh tokens, each time a refresh token is used to get a new access token, a *new* refresh token is also issued, and the old one is invalidated. If an old refresh token is reused, it indicates a breach, and the authorization server can revoke the entire token family.

### OIDC ID Token vs Access Token

- **ID Token**: A JWT containing claims about the authenticated user (e.g., name, email). Intended to be read by the *client* to understand who logged in.
- **Access Token**: An opaque string or JWT representing the authorization to access a resource. Intended to be read by the *Resource Server* (API).

## JWT Architecture & Verification

JSON Web Tokens (JWT) are widely used for stateless authentication.

### Structure
- **Header**: Contains metadata about the token, such as the algorithm used (`alg`) and the key ID (`kid`).
- **Payload**: Contains the claims (statements about the entity and additional data).
- **Signature**: Used to verify that the sender of the JWT is who it says it is and to ensure that the message wasn't changed along the way.

### Asymmetric vs Symmetric Signatures
- **Symmetric (HS256)**: Uses a single shared secret key to both sign and verify the token. Hard to manage across distributed microservices.
- **Asymmetric (RS256/ES256)**: Uses a private key to sign the token and a public key to verify it. Microservices only need the public key.

### JWKS Rotation Endpoint
JSON Web Key Set (JWKS) is an endpoint exposing public keys. Microservices can fetch and cache these keys to verify JWT signatures locally. Keys are rotated periodically for security.

### Standard Claims Validation
- `iss` (Issuer): Who issued the token?
- `aud` (Audience): Who is the token intended for?
- `exp` (Expiration Time): Is the token still valid?
- `nbf` (Not Before): Is the token active yet?
- `sub` (Subject): Who is the token about?
- `scope`: What permissions are granted?

## Gateway vs Sidecar Authentication

### API Gateway (Perimeter Validation)
Centralized entry point. Validates tokens before routing requests to internal microservices. Good for coarse-grained security but vulnerable to lateral movement if an internal service is compromised.

### Envoy Sidecar Local Verification (ext_authz)
In a service mesh, a sidecar proxy (like Envoy) runs alongside each microservice container. It intercepts all incoming requests and can perform local verification (using `ext_authz` filters) against cached JWKS, enforcing fine-grained security policies.

## Mutual TLS (mTLS) & Service Mesh

### Cryptographic Peer Authentication at L4/L7
mTLS ensures traffic between microservices is encrypted and mutually authenticated. Both the client and the server present X.509 certificates to prove their identity.

### SPIFFE and SPIRE
- **SPIFFE ID**: A uniform format to identify workloads (e.g., `spiffe://example.com/ns/default/sa/payment-service`).
- **SPIRE**: A production-ready implementation of the SPIFFE APIs. It issues short-lived SVIDs (SPIFFE Verifiable Identity Documents, usually X.509 certificates) and handles dynamic X.509 certificate renewal without downtime.

## Threat Models

1. **Confused Deputy**: An entity with high privileges is tricked into performing actions on behalf of a lower-privileged entity. Mitigation: Use audience (`aud`) and scopes, or pass the original user context.
2. **Token Replay**: An attacker intercepts a token and uses it to access resources. Mitigation: Short token expiration times, TLS/mTLS, and token binding (DPoP).
3. **JWT alg=none Vulnerability**: If the server accepts `alg: "none"`, it bypasses signature verification. Mitigation: Hardcode allowed algorithms during verification.
4. **MITM (Man in the Middle)**: Intercepting traffic. Mitigation: TLS for external, mTLS for internal communication.

## Common Pitfalls
1. **Treating internal network as trusted**: Failing to implement mTLS and authentication for internal service-to-service calls.
2. **Accepting any JWT algorithm**: Vulnerability to `alg=none` or confusing asymmetric keys with HMAC.
3. **Long-lived Access Tokens**: Not using refresh tokens, increasing the risk window if a token is stolen.

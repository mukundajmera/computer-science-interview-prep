# Semantic Retrieval Platform - Common Pitfalls

This document outlines common failure modes when designing the Semantic Retrieval Platform, explaining the root causes, actionable mitigations, and validation/monitoring signals.

## 1. Client-Side or Post-Response ACL Trust

**Signal:** The design retrieves chunks using ANN search first, and then assumes the downstream LLM or the client application will filter out unauthorized content, relies solely on ANN ACL prefilters without authoritative validation, or attempts to use post-response filtering.

**Root cause:** Post-response or client-side ACL filtering is inherently unsafe and leaks data, regardless of overfetch bounds or candidate budgets. Overfetch cannot make post-response filtering safe, and ANN ACL prefilters alone are not true authorization. ANN (Approximate Nearest Neighbor) is approximate; relying only on index metadata filters risks leaking content if there is filter/index drift.

**Mitigation:** Enforce strict authoritative ACL checks server-side before any content is returned (i.e., candidate validation after ANN retrieval). Note that this authoritative validation may reduce the final top-k returned to the user, but it guarantees secure data isolation.

**Validation/Monitoring signal:** Verify the system performs authoritative server-side candidate validation against a source of truth after ANN retrieval and prior to returning any results. Monitor empty-hit rates and reduced top-k counts segmented by tenant.

## 2. ANN Scores Treated as Answer Quality

**Signal:** The design uses an uncalibrated, universal raw embedding distance (cosine or L2) as an absolute threshold for whether a chunk answers the user's question, confusing retrieval pruning with answer correctness.

**Root cause:** Embedding distances measure semantic similarity in a specific vector space, not logical correctness or factual relevance. While a calibrated, model-specific threshold can be used to prune low-relevance candidates, a high similarity score does not establish that the text contains the factual answer (e.g., an opposite statement might have a high semantic overlap).

**Mitigation:** Distinguish between validated candidate pruning and answer-quality claims. Treat ANN scores as ranking signals or use carefully calibrated, index-specific distance cutoffs merely to prune the candidate set. Use a dedicated reranker or downstream LLM to evaluate actual factual relevance.

**Validation/Monitoring signal:** Ensure the system does not claim answer correctness based on raw vector distance or use uncalibrated universal thresholds. Validate any pruning thresholds against an evaluation gold set and track end-to-end recall@k and MRR/NDCG.

## 3. Embedding and Index Version Drift

**Signal:** The system dynamically updates its embedding model but does not re-embed existing chunks or separate vectors by model version in the index.

**Root cause:** Vectors generated by different models (or even different versions of the same model) exist in entirely different semantic spaces. Mixing them in the same index or comparing them leads to meaningless distances and broken retrieval.

**Mitigation:** Version every vector by `embedding_model_id`. Maintain separate indexes or partitioned namespaces for different model versions. Reindex the corpus completely before cutting over to a new model.

**Validation/Monitoring signal:** Assert that query vector models strictly match the candidate index's model version. Monitor shadow query parity during model migrations.

## 4. Unconditional Reranking

**Signal:** The design mandates an expensive cross-encoder reranking step for every query, regardless of the tenant's latency budget or query complexity.

**Root cause:** Cross-encoders are compute-heavy and significantly increase latency. Applying them unconditionally violates the strict p95 < 200ms latency constraint, especially during peak loads.

**Mitigation:** Implement optional reranking. Control rerank usage via tenant-specific configurations, dynamic latency budgets, or feature flags.

**Validation/Monitoring signal:** Measure p50, p95, and p99 query latencies. Track the rerank invocation rate and enforce backpressure or fallback to raw ANN when latency budgets are exhausted.

## 5. Ignored Freshness or Source Citation Traceability

**Signal:** The platform returns raw text chunks without mapping them back to the original source document offsets, or it fails to support timely re-indexing, leaving stale data in the index.

**Root cause:** Incomplete data models that strip metadata during chunking. Relying on slow batch pipelines that violate the < 5 minutes freshness requirement.

**Mitigation:** Persist document provenance (source document ID, text span, and offsets) alongside every chunk. Use streaming ingestion or micro-batch pipelines to ensure document updates are indexed rapidly.

**Validation/Monitoring signal:** Inspect the API response shape to ensure citation traceability is included. Monitor index queue lag and measure the ingestion-to-searchable delay.

## 6. Unsafe Cache Scope and Cost Overruns

**Signal:** Caching candidate results solely by the user's raw query string without incorporating the tenant ID or ACL context, or failing to address permission revocation for the same principal. Alternatively, unbounded ingestion leading to massive vector database costs.

**Root cause:** Ignoring multi-tenant isolation in the caching layer leads to cross-tenant data leaks. Caching by ACL without verifying current permissions on cache hits allows revoked principals to continue accessing cached data. Unrestricted chunking and embedding without deduplication or rate-limiting causes cost explosions.

**Mitigation:** Partition caches strictly by a composite key of `tenant_id`, `user_id`/ACL, and `query`. Require authoritative current ACL validation on every cache hit before returning content, plus ACL-version-aware invalidation or short expiry when permissions change. Enforce backpressure on reindex jobs and use deduplication to bound embedding operations.

**Validation/Monitoring signal:** Conduct explicit security reviews on cache key generation and cache hit authorization checks. Monitor cache hit rates, permission-revocation cache miss rates, and per-tenant API spend (embedding jobs, vector storage, and rerank calls).

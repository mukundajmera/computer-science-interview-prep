# Networking and Protocols: Cards 001-020 Answer Key

### Card 1
Front: What was the primary limitation of HTTP/1.0 regarding TCP connections?

**Answer:** HTTP/1.0 required opening a new TCP connection for every single request/response pair.

**Explanation:** Because setting up a TCP connection requires a 3-way handshake, creating a new connection for every resource (HTML, CSS, images) caused significant latency and overhead, slowing down page loads.

**Boundary/Misconception:** People often think HTTP/1.0 couldn't fetch multiple files at all. It could, but it had to do so sequentially, establishing a new connection each time.

**Source:** [MDN - Evolution of HTTP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Basics_of_HTTP/Evolution_of_HTTP)

### Card 2
Front: How did HTTP/1.1 attempt to solve the connection overhead of HTTP/1.0?

**Answer:** HTTP/1.1 introduced persistent connections (keep-alive) by default.

**Explanation:** With persistent connections, a single TCP connection can be kept open and reused for multiple HTTP requests and responses, eliminating the need to perform the TCP handshake for every resource.

**Boundary/Misconception:** Persistent connections solve the connection setup overhead, but they do not inherently solve head-of-line blocking for the requests themselves without multiplexing.

**Source:** [MDN - Connection management in HTTP/1.x](https://developer.mozilla.org/en-US/docs/Web/HTTP/Connection_management_in_HTTP_1.x)

### Card 3
Front: What is HTTP-layer Head-of-Line (HoL) blocking in the context of HTTP/1.1?

**Answer:** A situation where a single slow request prevents subsequent requests on the same TCP connection from being completed.

**Explanation:** In HTTP/1.1, responses must be returned in the exact order the requests were sent. If the first request takes a long time to process, all other queued responses are blocked behind it, even if they are ready.

**Boundary/Misconception:** This is specifically HTTP-layer HoL blocking, which is different from TCP-layer HoL blocking caused by packet loss.

**Source:** [High Performance Browser Networking - HTTP/1.X](https://hpbn.co/http1x/)

### Card 4
Front: Why was HTTP pipelining in HTTP/1.1 rarely successful in practice?

**Answer:** It still suffered from HTTP Head-of-Line blocking and many intermediate proxies/routers implemented it incorrectly or dropped pipelined requests.

**Explanation:** While pipelining allowed sending multiple requests without waiting for the first response, the responses still had to be returned in order. Due to buggy middleboxes, most browsers eventually disabled pipelining by default.

**Boundary/Misconception:** Pipelining is often confused with multiplexing. Pipelining is strictly sequential response ordering, whereas multiplexing (in HTTP/2) allows interleaved responses.

**Source:** [MDN - HTTP/1.1 pipelining](https://developer.mozilla.org/en-US/docs/Web/HTTP/Connection_management_in_HTTP_1.x#http_pipelining)

### Card 5
Front: How does HTTP/2 solve HTTP-layer HoL blocking?

**Answer:** HTTP/2 introduces binary framing and stream multiplexing over a single TCP connection.

**Explanation:** By breaking HTTP messages down into independent binary frames that belong to specific "streams", HTTP/2 can interleave frames from multiple requests and responses simultaneously without them blocking each other.

**Boundary/Misconception:** HTTP/2 only solves HTTP-layer HoL blocking. It still runs over a single TCP connection, meaning it is still vulnerable to TCP-layer HoL blocking.

**Source:** [Google Developers - Introduction to HTTP/2](https://developers.google.com/web/fundamentals/performance/http2)

### Card 6
Front: What is the purpose of HPACK in HTTP/2?

**Answer:** HPACK compresses HTTP headers to reduce overhead.

**Explanation:** In HTTP/1.1, headers are sent as plain text repeatedly with every request, which wastes bandwidth. HPACK uses a static dictionary for common headers and a dynamic dictionary for custom headers, along with Huffman coding, to drastically shrink header sizes.

**Boundary/Misconception:** HPACK doesn't compress the body (which uses gzip/brotli), it only compresses the metadata/headers.

**Source:** [RFC 7541 - HPACK: Header Compression for HTTP/2](https://datatracker.ietf.org/doc/html/rfc7541)

### Card 7
Front: What is Server Push in HTTP/2?

**Answer:** A feature allowing the server to proactively send resources to the client before the client explicitly requests them.

**Explanation:** If a client requests `index.html`, the server knows it will also need `style.css`. With Server Push, the server can push `style.css` alongside the HTML response, saving a round trip. 

**Boundary/Misconception:** Server Push has largely been deprecated in modern browsers (like Chrome) due to complexities with browser caching (pushing resources the client already has).

**Source:** [Chrome Developers - Removing HTTP/2 Server Push](https://developer.chrome.com/blog/removing-push/)

### Card 8
Front: Despite multiplexing, what type of Head-of-Line blocking does HTTP/2 still suffer from?

**Answer:** TCP-layer Head-of-Line blocking.

**Explanation:** Because HTTP/2 multiplexes all streams over a single TCP connection, if a single TCP packet is lost, the entire TCP connection halts until that packet is retransmitted. This blocks all HTTP/2 streams, even those whose packets arrived successfully.

**Boundary/Misconception:** Assuming multiplexing solves all blocking. Multiplexing only solves application-layer blocking; transport-layer blocking remains.

**Source:** [Cloudflare - What is HTTP/3?](https://www.cloudflare.com/learning/performance/what-is-http3/)

### Card 9
Front: Why does HTTP/2 suffer from TCP-layer HoL blocking?

**Answer:** TCP guarantees ordered, reliable delivery of all bytes in a single stream.

**Explanation:** TCP is unaware of HTTP/2's independent streams. To TCP, the entire HTTP/2 connection is just one continuous byte stream. If a packet is lost, TCP must pause delivery to the application until the missing packet is recovered, ensuring ordered delivery.

**Boundary/Misconception:** This isn't a flaw in HTTP/2 itself, but a limitation of using TCP as the transport layer for multiplexed data.

**Source:** [High Performance Browser Networking - TCP Head-of-Line Blocking](https://hpbn.co/building-blocks-of-tcp/#head-of-line-blocking)

### Card 10
Front: What fundamental transport protocol does HTTP/3 (QUIC) use instead of TCP?

**Answer:** User Datagram Protocol (UDP).

**Explanation:** HTTP/3 relies on QUIC, which is built on top of UDP. UDP provides a fast, connectionless datagram service, and QUIC implements its own reliability, congestion control, and stream multiplexing on top of it.

**Boundary/Misconception:** People sometimes think QUIC is unencrypted or unreliable because it uses UDP. QUIC adds reliability and mandatory encryption over UDP.

**Source:** [IETF - QUIC: A UDP-Based Multiplexed and Secure Transport](https://datatracker.ietf.org/doc/html/rfc9000)

### Card 11
Front: How does QUIC completely eliminate Head-of-Line blocking across streams?

**Answer:** QUIC implements multiplexing natively at the transport layer, so streams are independent.

**Explanation:** Because QUIC handles streams at the transport layer, if a packet belonging to Stream A is lost, only Stream A is delayed awaiting retransmission. Packets for Stream B can continue to be processed immediately by the application.

**Boundary/Misconception:** QUIC only eliminates HoL blocking *across* streams. Within a single stream, byte order is still guaranteed, so HoL blocking still exists *within* an individual stream.

**Source:** [RFC 9000 - QUIC Multiplexing](https://datatracker.ietf.org/doc/html/rfc9000#section-2)

### Card 12
Front: What cryptographic protocol is built directly into QUIC?

**Answer:** TLS 1.3.

**Explanation:** Unlike TCP where TLS operates as a separate layer on top, QUIC integrates TLS 1.3 directly into its transport handshake. This tight coupling improves security and reduces connection setup time.

**Boundary/Misconception:** QUIC does not use TLS 1.2; it mandates TLS 1.3 to ensure 1-RTT handshakes and strong encryption by default.

**Source:** [RFC 9001 - Using TLS to Secure QUIC](https://datatracker.ietf.org/doc/html/rfc9001)

### Card 13
Front: How many Round Trip Times (RTT) are required for a standard TCP + TLS 1.3 handshake?

**Answer:** 2 RTTs.

**Explanation:** A standard secure connection requires 1 RTT for the TCP handshake (SYN, SYN-ACK, ACK) and a 2nd RTT for the TLS 1.3 handshake (ClientHello, ServerHello). Only then can application data be sent.

**Boundary/Misconception:** Older TLS 1.2 required 3 RTTs (1 for TCP, 2 for TLS). TLS 1.3 reduced this, but the separation of TCP and TLS still requires 2 RTTs total.

**Source:** [Cloudflare - TLS 1.3 Overview](https://blog.cloudflare.com/rfc-8446-aka-tls-1-3/)

### Card 14
Front: How does QUIC achieve a 1-RTT initial handshake?

**Answer:** By combining the transport and cryptographic handshakes into a single exchange.

**Explanation:** Because QUIC integrates TLS 1.3, the client sends its transport parameters and cryptographic ClientHello in the very first packet. The server responds with its transport parameters and ServerHello, allowing data transmission after just 1 RTT.

**Boundary/Misconception:** 1-RTT is for the *initial* connection to a new server. Subsequent connections can be 0-RTT.

**Source:** [RFC 9000 - Connection Establishment](https://datatracker.ietf.org/doc/html/rfc9000#section-7)

### Card 15
Front: What is 0-RTT session resumption in QUIC?

**Answer:** A mechanism allowing a client to send application data in its very first packet if it has previously communicated with the server.

**Explanation:** The client caches cryptographic parameters (like a session ticket) from a previous connection. It uses these to encrypt early data alongside the connection request, meaning zero round trips are needed before sending data.

**Boundary/Misconception:** 0-RTT is not unique to QUIC; TLS 1.3 over TCP also supports 0-RTT, but QUIC optimizes it further.

**Source:** [RFC 9001 - 0-RTT](https://datatracker.ietf.org/doc/html/rfc9001#section-4.6)

### Card 16
Front: What is the primary security risk associated with 0-RTT session resumption in QUIC?

**Answer:** Replay attacks.

**Explanation:** Because 0-RTT data is encrypted with an older, cached key, an attacker could intercept the 0-RTT packet and resend (replay) it to the server multiple times before the server updates its anti-replay mechanisms.

**Boundary/Misconception:** 0-RTT doesn't inherently leak data (it's still encrypted), but it allows attackers to duplicate actions.

**Source:** [Cloudflare - The Replay Attack Problem with 0-RTT](https://blog.cloudflare.com/introducing-0-rtt/#the-replay-attack)

### Card 17
Front: What type of requests are safe to send during a 0-RTT resumption?

**Answer:** Idempotent requests, such as HTTP GET.

**Explanation:** Because of the risk of replay attacks, 0-RTT should only be used for actions that do not change server state. If a GET request is replayed, the server simply returns the same data, causing no harm. 

**Boundary/Misconception:** Non-idempotent requests (like POST requests modifying data or processing payments) must wait for a 1-RTT handshake to ensure the connection is fresh and protected against replay.

**Source:** [RFC 8446 - TLS 1.3 0-RTT Data](https://datatracker.ietf.org/doc/html/rfc8446#section-8)

### Card 18
Front: In traditional TCP, what 4-tuple identifies a connection?

**Answer:** Source IP, Source Port, Destination IP, Destination Port.

**Explanation:** TCP routing and connections strictly rely on this 4-tuple. If any of these four values change, the TCP connection is broken and must be re-established.

**Boundary/Misconception:** Assuming TCP has some internal ID; the IP addresses and ports *are* the unique identifier for TCP state.

**Source:** [TCP/IP Illustrated - Connection Establishment](https://en.wikipedia.org/wiki/Transmission_Control_Protocol)

### Card 19
Front: Why do mobile networks cause issues for traditional TCP connections during handovers?

**Answer:** Moving between networks (e.g., Wi-Fi to cellular) changes the client's Source IP address, breaking the TCP 4-tuple.

**Explanation:** When a phone switches from Wi-Fi to 5G, its IP address changes. Because TCP identifies connections using the IP address, the change forces the connection to drop, requiring a full re-handshake and disrupting user experience.

**Boundary/Misconception:** The issue isn't signal dropping, but rather the logical addressing changing, violating TCP's strict 4-tuple rule.

**Source:** [High Performance Browser Networking - Mobile Networks](https://hpbn.co/mobile-networks/)

### Card 20
Front: How does QUIC's 64-bit Connection ID enable seamless connection migration?

**Answer:** QUIC identifies connections using an explicit Connection ID rather than the IP/Port 4-tuple.

**Explanation:** If a client's IP address changes (e.g., moving from Wi-Fi to Cellular), the QUIC packets still contain the same Connection ID. The server recognizes the ID and seamlessly continues the connection over the new network without dropping it.

**Boundary/Misconception:** Connection IDs are not static forever; they can be updated during a connection to prevent tracking (privacy), but they decouple the connection logical state from the physical IP address.

**Source:** [RFC 9000 - Connection Migration](https://datatracker.ietf.org/doc/html/rfc9000#section-9)

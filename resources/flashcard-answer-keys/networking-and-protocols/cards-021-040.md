# Networking and Protocols: Cards 21-40 Answer Key

### Card 21
Front: What is the primary difference in directionality between WebSockets and Server-Sent Events (SSE)?

**Answer:** WebSockets are bidirectional, while SSE is strictly unidirectional (server-to-client).

**Explanation:** WebSockets provide a full-duplex TCP connection, allowing both client and server to send messages at any time. Server-Sent Events (SSE) establish a long-lived HTTP connection where only the server pushes data to the client.

**Boundary/Misconception:** Many assume SSE is a completely different transport layer, but it relies on standard HTTP.

**Source:** [MDN - Server-sent events vs WebSockets](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)

### Card 22
Front: Which protocol is better suited for a real-time trading application: SSE or WebSockets?

**Answer:** WebSockets.

**Explanation:** Real-time trading requires low-latency, bidirectional communication to push market data to the client and instantly receive trade orders from the client. WebSockets support this efficiently. SSE only allows server-to-client pushes.

**Boundary/Misconception:** Assuming SSE's simplicity makes it universally better; SSE fails when frequent client-to-server updates are needed.

**Source:** [MDN - WebSockets API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)

### Card 23
Front: How does Server-Sent Events (SSE) handle reconnections compared to WebSockets?

**Answer:** SSE has built-in automatic reconnection, while WebSockets require custom reconnection logic.

**Explanation:** The EventSource interface for SSE automatically attempts to reconnect if the connection drops. For WebSockets, developers must write manual retry and backoff logic to re-establish the connection.

**Boundary/Misconception:** Developers often assume WebSockets have built-in fault tolerance for reconnections, which they don't.

**Source:** [MDN - EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)

### Card 24
Front: What underlying protocol does gRPC use for transport?

**Answer:** HTTP/2.

**Explanation:** gRPC mandates HTTP/2 for its transport layer to utilize features like multiplexing, header compression (HPACK), and server streaming, which are essential for its performance characteristics.

**Boundary/Misconception:** A common mistake is thinking gRPC uses a custom TCP/UDP transport protocol, but it strictly relies on HTTP/2.

**Source:** [gRPC Motivation and Design Principles](https://grpc.io/blog/principles/)

### Card 25
Front: What serialization format is typically used with gRPC?

**Answer:** Protocol Buffers (Protobuf).

**Explanation:** Protobuf is a strongly-typed, binary serialization format. It is much more compact and faster to parse than text-based formats like JSON, which is a key reason for gRPC's performance efficiency.

**Boundary/Misconception:** Thinking gRPC can only use Protobuf. While it's the default, gRPC can technically be used with JSON or other serialization formats.

**Source:** [gRPC Basics - Protocol Buffers](https://grpc.io/docs/what-is-grpc/core-concepts/)

### Card 26
Front: Why might gRPC be preferred over REST for internal microservices communication?

**Answer:** gRPC offers higher performance through binary serialization (Protobuf) and HTTP/2 multiplexing, along with strong typing via interface definitions.

**Explanation:** Internal microservices often communicate heavily. gRPC reduces payload size and CPU overhead for parsing compared to JSON/REST. Strongly-typed schemas also prevent API mismatches between services.

**Boundary/Misconception:** Believing gRPC is always better than REST. REST is still often preferred for public APIs due to wider ecosystem support and human readability.

**Source:** [gRPC vs REST](https://cloud.google.com/blog/products/api-management/understanding-grpc-openapi-and-rest-and-when-to-use-them)

### Card 27
Front: What are the main limitations of using gRPC directly from a web browser?

**Answer:** Browsers do not natively expose low-level HTTP/2 framing required by standard gRPC, requiring a proxy like gRPC-Web.

**Explanation:** To use gRPC from a web client, developers must use gRPC-Web, which translates gRPC requests into HTTP/1.1 or HTTP/2 requests that the browser can handle, usually requiring an Envoy proxy on the backend.

**Boundary/Misconception:** Assuming modern browsers can use standard gRPC directly because they support HTTP/2.

**Source:** [gRPC-Web](https://github.com/grpc/grpc-web)

### Card 28
Front: In what scenario might a corporate firewall force a fallback from HTTP/3 to HTTP/2?

**Answer:** When the firewall blocks outbound UDP traffic on port 443.

**Explanation:** HTTP/3 runs over QUIC, which uses UDP. Many legacy corporate firewalls block UDP except for DNS (port 53). In such cases, clients must fallback to HTTP/2 over TCP on port 443.

**Boundary/Misconception:** Assuming HTTP/3 operates over TCP like previous HTTP versions.

**Source:** [RFC 9000 - QUIC](https://datatracker.ietf.org/doc/html/rfc9000)

### Card 29
Front: Why was QUIC built on top of UDP rather than creating an entirely new IP protocol layer?

**Answer:** To enable rapid deployment across the internet without requiring hardware upgrades to routers and middleboxes.

**Explanation:** If QUIC were a new IP protocol, every router and NAT device on the internet would need firmware updates to recognize it. By encapsulating QUIC inside UDP, existing middleboxes pass the traffic without modification.

**Boundary/Misconception:** Thinking UDP was chosen for its 'unreliable' nature; QUIC actually implements reliability on top of UDP.

**Source:** [QUIC: A UDP-Based Multiplexed and Secure Transport](https://datatracker.ietf.org/doc/html/rfc9000)

### Card 30
Front: What are the overhead characteristics of WebSockets after the initial HTTP handshake is complete?

**Answer:** WebSockets have very low per-message overhead, typically just 2 to 10 bytes of framing.

**Explanation:** Once the HTTP handshake is upgraded to a WebSocket connection, messages are exchanged with minimal binary framing, eliminating the bulky HTTP headers required for every REST request.

**Boundary/Misconception:** Assuming WebSocket messages still carry HTTP headers.

**Source:** [RFC 6455 - The WebSocket Protocol](https://datatracker.ietf.org/doc/html/rfc6455)

### Card 31
Front: How does QUIC handle congestion control if UDP has no native congestion control mechanisms?

**Answer:** QUIC implements its own congestion control algorithms (like CUBIC or BBR) entirely in user space.

**Explanation:** Since UDP lacks native congestion control, the QUIC protocol layer actively monitors packet loss, RTT, and pacing to manage congestion, replicating and often improving upon TCP's kernel-space congestion control.

**Boundary/Misconception:** Believing QUIC lacks congestion control just because it uses UDP.

**Source:** [RFC 9000 - QUIC Transport](https://datatracker.ietf.org/doc/html/rfc9000)

### Card 32
Front: What is the difference in how HTTP/2 and HTTP/3 handle stream prioritization?

**Answer:** HTTP/2 handles prioritization via complex stream dependencies and weights, whereas HTTP/3 uses a simpler scheme called Extensible Prioritization Scheme.

**Explanation:** HTTP/2's dependency tree proved too complex and was often poorly implemented. HTTP/3 abandoned it for a simpler system (RFC 9218) that uses absolute urgency levels and an incremental flag.

**Boundary/Misconception:** Assuming HTTP/3 simply copied HTTP/2's exact stream prioritization model.

**Source:** [RFC 9218 - Extensible Prioritization Scheme for HTTP](https://datatracker.ietf.org/doc/html/rfc9218)

### Card 33
Front: Why is HTTP/3 particularly advantageous for mobile users on unreliable networks?

**Answer:** QUIC supports connection migration via Connection IDs, allowing the session to survive changing IP addresses.

**Explanation:** When a mobile device switches from Wi-Fi to cellular, its IP address changes. TCP connections break because they are bound by the 4-tuple (IPs and Ports). QUIC uses a unique Connection ID, allowing the stream to continue seamlessly.

**Boundary/Misconception:** Assuming HTTP/3's main advantage for mobile is only speed, ignoring connection resilience.

**Source:** [RFC 9000 - Connection Migration](https://datatracker.ietf.org/doc/html/rfc9000#name-connection-migration)

### Card 34
Front: Can you describe a scenario where Server-Sent Events (SSE) is preferable to WebSockets for LLM token streaming?

**Answer:** When generating text where data flows strictly in one direction (server to client) and simplicity is preferred.

**Explanation:** LLM streaming only requires the server to push tokens to the client. SSE is perfectly suited for this unidirectional flow, works over standard HTTP/1.1 or HTTP/2, and is natively supported by the EventSource API without the complexity of WebSockets.

**Boundary/Misconception:** Thinking WebSockets are strictly required for any real-time streaming.

**Source:** [OpenAI API Documentation - Streaming](https://platform.openai.com/docs/api-reference/streaming)

### Card 35
Front: What happens to a multiplexed HTTP/2 connection if a single TCP packet is dropped?

**Answer:** All multiplexed streams on that connection stall, experiencing Head-of-Line (HoL) blocking.

**Explanation:** Because HTTP/2 relies on a single TCP connection, if one packet is lost, TCP halts delivery of all subsequent packets (even those for different streams) until the lost packet is retransmitted.

**Boundary/Misconception:** Believing HTTP/2's multiplexing solves TCP-layer Head-of-Line blocking; it only solves HTTP-layer HoL blocking.

**Source:** [High Performance Browser Networking - HTTP/2](https://hpbn.co/http2/)

### Card 36
Front: What happens to a multiplexed HTTP/3 connection if a single UDP datagram is dropped?

**Answer:** Only the specific stream associated with that datagram experiences delay; other streams continue unaffected.

**Explanation:** HTTP/3 over QUIC implements streams independently. Since there is no underlying TCP ordered-delivery guarantee, a dropped UDP packet only blocks the stream it belongs to, eliminating connection-wide HoL blocking.

**Boundary/Misconception:** Assuming QUIC completely prevents packet loss; it handles loss better but doesn't eliminate the physics of dropped packets.

**Source:** [RFC 9000 - Streams](https://datatracker.ietf.org/doc/html/rfc9000#name-streams)

### Card 37
Front: How does HTTP/1.1 persistent connections (`Connection: keep-alive`) impact server resource utilization?

**Answer:** It forces the server to maintain open sockets for idle clients, potentially exhausting file descriptors.

**Explanation:** While `keep-alive` reduces connection setup latency, a server must keep the TCP connection state in memory. For highly concurrent systems with many idle clients, this can lead to resource exhaustion.

**Boundary/Misconception:** Assuming persistent connections have zero cost to the server.

**Source:** [High Performance Browser Networking - HTTP/1.x](https://hpbn.co/http1x/)

### Card 38
Front: What is the role of the TLS 1.3 server hello in the QUIC handshake process?

**Answer:** QUIC bakes TLS 1.3 directly into its initial handshake, exchanging cryptographic keys alongside transport parameters.

**Explanation:** Unlike TCP where the transport handshake (SYN/ACK) completes before the TLS handshake begins, QUIC combines them. The client sends a combined QUIC + TLS Client Hello, and the server responds with a combined Server Hello, achieving a 1-RTT connection.

**Boundary/Misconception:** Thinking QUIC uses a proprietary encryption scheme rather than standard TLS 1.3.

**Source:** [RFC 9001 - Using TLS to Secure QUIC](https://datatracker.ietf.org/doc/html/rfc9001)

### Card 39
Front: Why are older APIs often left on HTTP/1.1 instead of upgrading to HTTP/2 or HTTP/3?

**Answer:** Because simple REST/JSON requests over HTTP/1.1 are widely supported, easy to debug, and sufficient for low-throughput operations.

**Explanation:** The complexity of setting up HTTP/2 or HTTP/3 (requiring TLS and complex proxies) often outweighs the benefits for basic CRUD APIs that don't need multiplexing or real-time streaming.

**Boundary/Misconception:** Assuming newer HTTP versions deprecate HTTP/1.1; HTTP/1.1 remains the dominant protocol for simple machine-to-machine APIs.

**Source:** [RFC 9112 - HTTP/1.1](https://datatracker.ietf.org/doc/html/rfc9112)

### Card 40
Front: What are the implications of QUIC encrypting almost all packet headers compared to TCP?

**Answer:** It prevents middleboxes (like firewalls and NATs) from inspecting or manipulating transport layer data.

**Explanation:** TCP headers (ports, flags, sequence numbers) are sent in plaintext, allowing middleboxes to interfere. QUIC encrypts almost all metadata, protecting privacy and preventing protocol ossification, as middleboxes can't rely on or modify the headers.

**Boundary/Misconception:** Assuming encryption in QUIC only protects the application payload; it also protects the transport layer metadata.

**Source:** [RFC 9000 - Header Protection](https://datatracker.ietf.org/doc/html/rfc9000#name-header-protection)

# HLD Projects - Flashcard Answers (21-40)

This document provides answers, common boundaries, and concept links for cards 21 to 40 in the HLD projects flashcards deck.

### Card 21
**Front:** How do you architect a Realtime Metrics Platform using tumbling windows and approximate counting algorithms?

**Answer:** Use tumbling windows via stream processors (Flink/Spark) to aggregate metrics in distinct time buckets, and rely on HyperLogLog or Count-Min Sketch for memory-efficient approximate counting.

**Explanation:** Tumbling windows provide strict time boundaries for rate calculations without overlapping, while approximate algorithms reduce the O(N) memory required for distinct tracking down to a constant bound.

**Boundary/Misconception:** Attempting to track exact counts for high-cardinality IP addresses or user IDs in a stream, which quickly leads to memory exhaustion.

### Card 22
**Front:** What stream processing techniques are used in a Bot Detection Platform to analyze traffic patterns with minimal latency?

**Answer:** Bot detection platforms utilize stream processing (like Flink) with sliding windows to analyze rate limits, sudden IP spikes, and request signatures in near real-time, matching traffic against known bad patterns.

**Explanation:** Sliding windows are critical here (unlike tumbling windows) to detect abuse that spans across fixed time boundaries (e.g. 500 requests at 1:59:59 and 500 at 2:00:01).

**Boundary/Misconception:** Relying purely on static rule-based firewalls (WAF) without historical or windowed context, which fails against distributed low-and-slow botnets.

**Source:** [`../../../04-hld-projects/bot-detection-platform/PROBLEM.md`](../../../04-hld-projects/bot-detection-platform/PROBLEM.md)

### Card 23
**Front:** How do you inject and propagate trace IDs across microservices in a Distributed Tracing system?

**Answer:** Inject a unique Trace ID at the entry API gateway, propagate it through HTTP headers (like W3C Trace Context) or RPC metadata on every inter-service call, and collect spans asynchronously via an agent.

**Explanation:** Consistent header propagation ensures that a single user request can be reconstructed as a DAG of spans across multiple microservices without requiring synchronous logging bottlenecks.

**Boundary/Misconception:** Generating new trace IDs at intermediate services, which breaks the end-to-end request lineage and makes distributed debugging impossible.

**Source:** [`../../../04-hld-projects/distributed-tracing/PROBLEM.md`](../../../04-hld-projects/distributed-tracing/PROBLEM.md)

### Card 24
**Front:** What is the system design for a Price Tracking Service that must continuously scrape and alert on millions of dynamic items?

**Answer:** Use a distributed cron scheduler to dispatch scrape tasks to a pool of proxy-rotated workers, parse the results, diff against the last known price in a fast KV store, and publish changes to a notification topic.

**Explanation:** Decoupling the scraper workers from the alerting mechanism ensures that rate limits or CAPTCHAs on target sites do not block the delivery of already-detected price drops.

**Boundary/Misconception:** Making the scrape-and-alert workflow synchronous, leading to severe cascading timeouts when target websites are slow.

**Source:** [`../../../04-hld-projects/price-tracking-service/PROBLEM.md`](../../../04-hld-projects/price-tracking-service/PROBLEM.md)

### Card 25
**Front:** How do you achieve idempotency and exactly-once processing in a Payment System architecture?

**Answer:** Ensure exactly-once processing by generating a unique idempotency key at the client, passing it through API gateways, and persisting it atomically with the transaction state using a database uniqueness constraint.

**Explanation:** The idempotency key guarantees that if a client retries a payment request due to a network timeout, the database rejects the duplicate insert or returns the previously successful result.

**Boundary/Misconception:** Relying on simple status checks before writing (read-then-write) without database locks or constraints, which is vulnerable to race conditions.

**Source:** [`../../../04-hld-projects/payment-system/PROBLEM.md`](../../../04-hld-projects/payment-system/PROBLEM.md)

### Card 26
**Front:** What database properties and transaction models are required to safely transfer funds in a Digital Wallet system?

**Answer:** Use an ACID-compliant relational database (like PostgreSQL or MySQL/InnoDB) utilizing distributed transactions (Two-Phase Commit) or Saga patterns, with row-level locks on the accounts involved.

**Explanation:** Row-level locks (`SELECT FOR UPDATE`) prevent concurrent requests from overdrafting an account, while strict ACID properties guarantee that a debit and credit either both succeed or both fail.

**Boundary/Misconception:** Using an eventually consistent NoSQL database for core ledger balances, which can temporarily expose negative balances or lose funds during partition heals.

**Source:** [`../../../04-hld-projects/digital-wallet/PROBLEM.md`](../../../04-hld-projects/digital-wallet/PROBLEM.md)

### Card 27
**Front:** How do you handle high-concurrency reservations and prevent double-booking in a Ticketing Platform?

**Answer:** Use a distributed lock (e.g., Redis) to tentatively hold a seat, followed by an atomic write with a uniqueness constraint (SeatID + EventID) in a relational database upon successful payment.

**Explanation:** The Redis lock provides a fast path to reject concurrent users trying to select the same seat, while the database constraint acts as the final source of truth against race conditions.

**Boundary/Misconception:** Locking the entire event or row for long periods while waiting for third-party payment gateways, which severely degrades ticketing throughput.

**Source:** [`../../../04-hld-projects/ticketing-platform/PROBLEM.md`](../../../04-hld-projects/ticketing-platform/PROBLEM.md)

### Card 28
**Front:** What is the architecture for an Online Auction system that requires strict bid consistency and real-time client updates?

**Answer:** Use an in-memory datastore (Redis) for real-time bid validation and leaderboards to minimize latency, backed by a message broker to asynchronously persist bids and push updates via WebSockets to connected clients.

**Explanation:** Strict consistency requires validating that every new bid is strictly higher than the current max bid. Using Redis with Lua scripts ensures this check is atomic and fast.

**Boundary/Misconception:** Writing bids directly to a traditional disk-based RDBMS synchronously before returning to the user, causing unacceptable latency in high-frequency sniper bidding scenarios.

**Source:** [`../../../04-hld-projects/online-auction/PROBLEM.md`](../../../04-hld-projects/online-auction/PROBLEM.md)

### Card 29
**Front:** How do you build an ultra-low latency in-memory order book for a Stock Exchange Matching Engine?

**Answer:** Implement the matching engine entirely in-memory using optimized data structures (like a Price-Time priority queue or Red-Black Tree), and use event sourcing to append trades to a high-speed sequential journal (e.g., Aeron) for durability.

**Explanation:** Disk I/O is too slow for high-frequency trading. State is kept purely in RAM, and fault tolerance is achieved by replaying the deterministic event journal if the process crashes.

**Boundary/Misconception:** Using external databases or network hops in the critical path of the matching algorithm, which destroys microsecond latency requirements.

**Source:** [`../../../04-hld-projects/stock-exchange-matching-engine/PROBLEM.md`](../../../04-hld-projects/stock-exchange-matching-engine/PROBLEM.md)

### Card 30
**Front:** What asynchronous patterns are used in a Brokerage Platform to execute trades and reconcile ledger balances?

**Answer:** Brokerage platforms use Event Sourcing and the Saga pattern over a highly available message bus (Kafka) to coordinate order validation, matching engine execution, and asynchronous ledger reconciliation.

**Explanation:** Decoupling matching from ledger updates allows the critical path (executing the trade) to remain fast, while the ledger reconciliation happens eventually and reliably via messaging.

**Boundary/Misconception:** Implementing large distributed transactions (2PC) across the matching engine and user ledgers, drastically reducing system throughput.

**Source:** [`../../../04-hld-projects/brokerage-platform/PROBLEM.md`](../../../04-hld-projects/brokerage-platform/PROBLEM.md)

### Card 31
**Front:** How does an E-commerce Backend handle shopping cart state and distributed inventory decrements during checkout?

**Answer:** Store the cart in a high-speed KV store (Redis) with a TTL. For checkout, transition to an RDBMS using Saga patterns or Outbox patterns to coordinate distributed inventory decrements and payment capture.

**Explanation:** Shopping carts are read/write heavy but transient, making Redis ideal. Checkout requires strict consistency, so transitioning to a transactional RDBMS guarantees inventory isn't oversold.

**Boundary/Misconception:** Decrementing inventory exactly when an item is added to the cart, causing available stock to deplete indefinitely if users abandon their carts.

**Source:** [`../../../04-hld-projects/ecommerce-backend/PROBLEM.md`](../../../04-hld-projects/ecommerce-backend/PROBLEM.md)

### Card 32
**Front:** How do you design a Distributed Job Scheduler to guarantee fault-tolerant execution of delayed and cron-based jobs?

**Answer:** Store jobs in a durable RDBMS or specialized queue. A cluster of coordinator nodes polls or subscribes to the database, leases jobs using atomic locks (`SELECT FOR UPDATE`), and dispatches them to worker nodes, updating state upon completion or timeout.

**Explanation:** The lease mechanism prevents multiple workers from executing the same job. If a worker dies, the lease expires, and the coordinator can safely reassign the job.

**Boundary/Misconception:** Using an in-memory only queue (like basic Redis without persistence) for cron jobs, which risks catastrophic task loss upon node failure.

**Source:** [`../../../04-hld-projects/job-scheduler/PROBLEM.md`](../../../04-hld-projects/job-scheduler/PROBLEM.md)

### Card 33
**Front:** How do you use Geohash or Quadtree indexes to efficiently query points of interest in a Proximity Service?

**Answer:** Convert 2D latitude/longitude coordinates into 1D Geohash strings or a Quadtree structure. This allows proximity queries to be executed as fast 1D string prefix matches or tree traversals in a database or memory cache.

**Explanation:** Geohashes group geographically close points into strings that share the same prefix. Finding nearby POIs is reduced to finding rows starting with the user's Geohash prefix.

**Boundary/Misconception:** Calculating the Haversine distance between the user and every single POI in the database (O(N)), which is computationally unfeasible at scale.

**Source:** [`../../../04-hld-projects/proximity-service-yelp/PROBLEM.md`](../../../04-hld-projects/proximity-service-yelp/PROBLEM.md)

### Card 34
**Front:** What is the system architecture for matching riders and drivers in a Ride Sharing application?

**Answer:** Drivers continuously stream their location to a location tracking service (using Redis Geo). A matching service uses a message broker (Kafka) to pull nearby available drivers and dispatches push notifications to find the best match.

**Explanation:** Separating the high-throughput driver location ingestion from the complex ride-matching algorithm prevents location updates from bogging down the transactional matching system.

**Boundary/Misconception:** Using persistent TCP connections between the rider and driver directly, bypassing the backend, which makes mediation and dispatching impossible.

**Source:** [`../../../04-hld-projects/ride-sharing/PROBLEM.md`](../../../04-hld-projects/ride-sharing/PROBLEM.md)

### Card 35
**Front:** How do you model road networks and perform hierarchical routing in a Google Maps-like system?

**Answer:** Represent the world as a graph of road segments. Pre-compute and partition routes using hierarchical pathfinding algorithms (like Contraction Hierarchies or A* with landmarks) and cache frequently requested routes.

**Explanation:** Running standard Dijkstra's algorithm on a continental-scale graph in real-time is too slow. Pre-computing shortcuts (Contraction Hierarchies) drastically reduces the search space.

**Boundary/Misconception:** Attempting to calculate routes dynamically from raw un-indexed map data for every user request, leading to massive CPU overload and latency.

**Source:** [`../../../04-hld-projects/google-maps/PROBLEM.md`](../../../04-hld-projects/google-maps/PROBLEM.md)

### Card 36
**Front:** What algorithms and caching layers are needed to build a fast, distributed Search Autocomplete service?

**Answer:** Store prefixes in a highly optimized Trie data structure, typically hosted in-memory (Redis/Memcached). Cache top results at the edge (CDN) for hot queries, and asynchronously aggregate new search terms to update the Trie offline.

**Explanation:** A Trie provides O(L) lookup time for a prefix of length L. Updating the Trie offline ensures read latency remains low even as search trends change.

**Boundary/Misconception:** Executing a SQL `LIKE 'prefix%'` query against a massive database for every keystroke, which will instantly overwhelm the DB.

**Source:** [`../../../04-hld-projects/search-autocomplete/PROBLEM.md`](../../../04-hld-projects/search-autocomplete/PROBLEM.md)

### Card 37
**Front:** How do you manage rate limits and deduplication effectively in a massive-scale Web Crawler?

**Answer:** Use a centralized URL frontier (Kafka or Redis) to enforce per-domain rate limits, and an efficient distributed Bloom Filter to check if a URL has already been crawled before dispatching it to worker nodes.

**Explanation:** A Bloom Filter uses a tiny fraction of the memory compared to a Hash Set for deduplication. The URL frontier ensures politeness by decoupling the discovery of links from the scheduling of downloads.

**Boundary/Misconception:** Storing every visited URL in a relational database and querying it synchronously, which becomes an immense bottleneck for crawler throughput.

**Source:** [`../../../04-hld-projects/web-crawler/PROBLEM.md`](../../../04-hld-projects/web-crawler/PROBLEM.md)

### Card 38
**Front:** What system design patterns are used to optimize hyper-local driver assignment in Quick Commerce Delivery?

**Answer:** Use Geohashing paired with Redis Pub/Sub or WebSockets to instantly broadcast delivery requests to a hyper-local radius. Algorithms prioritize drivers based on batching potential and current trajectory to minimize turnaround time.

**Explanation:** Quick commerce demands sub-15-minute delivery, so routing logic must proactively batch orders that share the same macro-route from the dark store, rather than purely 1:1 matching.

**Boundary/Misconception:** Relying strictly on historical ETAs without real-time traffic or in-store prep-time context, leading to drivers waiting idly at the pickup location.

### Card 39
**Front:** How do you manage complex task dependencies and state transitions in a Distributed Workflow Orchestrator?

**Answer:** Use an event-driven architecture with a centralized State Machine (e.g. Temporal, AWS Step Functions) backed by a scalable datastore to durably record workflow progress and handle retries, timeouts, and compensations (Sagas).

**Explanation:** A centralized orchestrator tracks the DAG of task execution, ensuring that if a step fails, proper rollback or compensation steps are reliably triggered without manual intervention.

**Boundary/Misconception:** Using ad-hoc peer-to-peer choreography (services calling each other via HTTP) for complex, multi-step workflows, resulting in unmanageable spaghetti architecture and lost state.

**Source:** [`../../../04-hld-projects/distributed-workflow-orchestrator/PROBLEM.md`](../../../04-hld-projects/distributed-workflow-orchestrator/PROBLEM.md)

### Card 40
**Front:** How do you scale a Realtime Gaming Leaderboard using Redis Sorted Sets and sharded ranking trees?

**Answer:** Use Redis Sorted Sets (ZSET) for O(log N) rank operations, and partition the leaderboard by logical boundaries (e.g., region, tier) or use an augmented tree structure to scale beyond a single node's memory.

**Explanation:** Redis ZSETs natively maintain a score-based ordering in memory. Sharding by tier (Bronze, Silver, Gold) avoids hot-key bottlenecks and memory limits on a single Redis instance.

**Boundary/Misconception:** Calculating ranks dynamically using SQL `COUNT()` queries over all players with a higher score, which degrades to O(N) and fails under high load.

**Source:** [`../../../04-hld-projects/realtime-gaming-leaderboard/PROBLEM.md`](../../../04-hld-projects/realtime-gaming-leaderboard/PROBLEM.md)

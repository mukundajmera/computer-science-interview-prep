# HLD Projects Flashcard Answers (Cards 1-20)

### Card 1
**Front:** What are the key trade-offs between fanout-on-write and fanout-on-read in a News Feed architecture?

**Answer:** Fanout-on-write (push) pre-computes feeds yielding fast reads (O(1)) but causes heavy write loads for users with many followers (celebrity problem). Fanout-on-read (pull) generates feeds dynamically, resulting in slow reads but cheap writes. Hybrid approaches push to active followers and pull from celebrities.

**Explanation:** To balance the system, most production news feeds use a hybrid model: pushing updates for normal users and pulling updates for users with massive followings to avoid write amplification.

**Boundary/Misconception:** Applying fanout-on-write universally typically fails for celebrity accounts because it creates massive, synchronous write amplification that can choke the system.

### Card 2
**Front:** How do you maintain persistent connections and efficiently route messages in a distributed Chat Service?

**Answer:** Clients maintain long-lived WebSockets to stateless Connection Servers. A Presence Service tracks user-to-server mappings in a fast store (e.g., Redis). When a message is sent, a Chat Server queries the Presence Service, then forwards the message via Pub/Sub or RPC to the specific Connection Server holding the recipient's socket.

**Explanation:** Decoupling connection management from message routing allows connection servers to scale horizontally to handle millions of idle sockets, while chat servers scale based on message throughput.

**Boundary/Misconception:** Assuming standard HTTP request-response is sufficient. HTTP polling is generally too slow and resource-intensive for real-time chat at scale.

**Source:** [`../../../04-hld-projects/chat-service/PROBLEM.md`](../../../04-hld-projects/chat-service/PROBLEM.md)

### Card 3
**Front:** What data model and read-path optimizations are used in a Social Graph Engine (e.g., TAO) to serve highly concurrent connection queries?

**Answer:** Social graphs model entities as "nodes" and relationships as "edges". Read optimizations include massive in-memory graph caching (like Memcached), modeling data in a graph DB (or RDBMS with adjacency lists), and sharding edges by node ID to ensure local traversals.

**Explanation:** Because social network queries often involve traversing relationships (e.g., "friends of friends"), localized data access and aggressive caching of recent edges are critical to sub-millisecond response times.

**Boundary/Misconception:** Attempting deep graph traversals (e.g., degree 3+) in real-time across a partitioned distributed database typically fails due to massive cross-shard RPC amplification.

**Source:** [`../../../04-hld-projects/social-graph-engine-tao/PROBLEM.md`](../../../04-hld-projects/social-graph-engine-tao/PROBLEM.md)

### Card 4
**Front:** How do you handle real-time conflict resolution in a Collaborative Document Editor using OT or CRDTs?

**Answer:** Operational Transformation (OT) uses a centralized server to sequence and transform concurrent edits so all clients converge. Conflict-Free Replicated Data Types (CRDTs) embed logical clocks and unique IDs into data structures, mathematically guaranteeing convergence without a central coordinator.

**Explanation:** OT is traditionally used by Google Docs, requiring a central sequencing server. CRDTs are newer and allow peer-to-peer syncing, but often incur larger metadata and memory overhead.

**Boundary/Misconception:** Assuming simple Last-Writer-Wins (LWW) works for text editing. LWW overwrites entire blocks, losing concurrent keystrokes rather than merging them.

**Source:** [`../../../04-hld-projects/collaborative-doc-editor/PROBLEM.md`](../../../04-hld-projects/collaborative-doc-editor/PROBLEM.md)

### Card 5
**Front:** What is the optimal architecture for broadcasting Live Comments to millions of concurrent viewers during a live event?

**Answer:** Use a Pub/Sub system (e.g., Redis Pub/Sub) and fan out to WebSocket servers holding client connections. To handle massive scale, batch comments per second, aggressively rate-limit, and sample/throttle comments rather than delivering every single message to every viewer.

**Explanation:** In a massive live stream (e.g., 1M viewers), delivering every comment is often impossible and unreadable. Throttling and batching at the WebSocket server level are generally required to prevent overwhelming client devices.

**Boundary/Misconception:** Attempting to guarantee exact delivery of all messages to all clients. In live broadcasting, eventual consistency and dropping messages under high load is an acceptable trade-off for stability.

### Card 6
**Front:** How do you design a Notification Service to ensure reliable delivery and avoid duplicate notifications across Email, SMS, and Push?

**Answer:** Use decoupled workers consuming from message queues (e.g., Kafka). Store a delivery log in a database (like Cassandra) to deduplicate via a unique `notification_id`. Employ retry queues with exponential backoff for third-party failures, and a preferences service to filter out muted channels.

**Explanation:** Third-party services (APNs, SendGrid) fail often. Asynchronous queues buffer these failures, while a persistent deduplication table prevents users from receiving the same alert twice during retries.

**Boundary/Misconception:** Relying purely on at-most-once delivery or synchronous API calls, which leads to lost notifications during downstream outages.

**Source:** [`../../../04-hld-projects/notification-service/PROBLEM.md`](../../../04-hld-projects/notification-service/PROBLEM.md)

### Card 7
**Front:** How does a Nearby Friends system efficiently update and query high-frequency ephemeral location data?

**Answer:** Rely on in-memory datastores (e.g., Redis with geospatial indexes like GeoHash) to process high write throughput. Periodically flush to persistent storage if history is needed. Broadcast location deltas to active friends via WebSockets to minimize full-payload pulls.

**Explanation:** Location updates happen constantly. Writing every coordinate change to a persistent disk database (like PostgreSQL) can bottleneck the system. Redis handles the high write rate and geospatial querying natively.

**Boundary/Misconception:** Storing real-time, high-frequency location data directly in a traditional RDBMS without an in-memory caching layer.

### Card 8
**Front:** What is the recommended strategy for asynchronously processing and filtering user uploads in a Content Moderation platform?

**Answer:** Uploads trigger events in a distributed queue (Kafka/SQS). A pipeline of stateless worker nodes processes the media (e.g., hashing, ML inference). Store state transitions in a DB. If flagged, route to a manual review queue; otherwise, approve and notify the client asynchronously.

**Explanation:** Content moderation (especially ML inference) is CPU-intensive and slow. Processing synchronously blocks the API. Event-driven pipelines allow the system to scale worker nodes based on queue depth.

**Boundary/Misconception:** Running heavy ML models synchronously in the request-response cycle of the web server.

**Source:** [`../../../04-hld-projects/content-moderation-platform/PROBLEM.md`](../../../04-hld-projects/content-moderation-platform/PROBLEM.md)

### Card 9
**Front:** How do you prevent hash collisions and ensure scalability when generating unique identifiers for a URL Shortener?

**Answer:** Use a distributed ID generator (like Snowflake or a DB ticket server) to assign a unique Base62 encoded integer to each URL. Alternatively, compute MD5/SHA256, take the first 7-8 characters, and handle collisions via a retry mechanism with appending salts.

**Explanation:** Pre-generating unique IDs using a Ticket Server or ZooKeeper guarantees no collisions and is faster than calculating and checking hashes on every single upload.

**Boundary/Misconception:** Relying solely on short random string generation without a robust collision detection and retry strategy.

**Source:** [`../../../04-hld-projects/url-shortener/PROBLEM.md`](../../../04-hld-projects/url-shortener/PROBLEM.md)

### Card 10
**Front:** What is the role of a metadata database versus blob storage nodes in a Distributed Cloud Storage (S3) architecture?

**Answer:** The metadata database (e.g., Cassandra/CockroachDB) strongly consistently tracks namespaces, ACLs, and block mappings. Blob storage nodes handle immutable, raw chunk storage. Decoupling them allows metadata to be optimized for complex queries and ACID transactions, while blob nodes scale for sheer IO throughput.

**Explanation:** Storing metadata alongside the raw bits scales poorly for searches and permissions. Decoupling allows independent scaling of storage capacity (blob nodes) and query throughput (metadata DB).

**Boundary/Misconception:** Attempting to store large binary payloads directly inside a relational database.

**Source:** [`../../../04-hld-projects/distributed-cloud-storage-s3/PROBLEM.md`](../../../04-hld-projects/distributed-cloud-storage-s3/PROBLEM.md)

### Card 11
**Front:** How do you manage data replication and consistent hashing in a Distributed Cache?

**Answer:** Consistent hashing places data and nodes on a virtual ring, minimizing data movement when nodes join/leave. Replication involves storing keys on the first node, and backing up on the next N nodes on the ring. Clients or proxy layers handle routing requests using the hash ring topology.

**Explanation:** Standard modulo hashing `hash(key) % N` typically breaks down if N changes, invalidating most of the cache. Consistent hashing limits reshuffling to `1/N` of the keys.

**Boundary/Misconception:** Assuming consistent hashing completely solves all hot keys. A viral key will still overwhelm its assigned node unless specifically handled via local caching or replication.

**Source:** [`../../../04-hld-projects/distributed-cache/PROBLEM.md`](../../../04-hld-projects/distributed-cache/PROBLEM.md)

### Card 12
**Front:** What is the most efficient storage strategy for handling expiration and cleanup in a Pastebin-like text storage service?

**Answer:** Use a DB table or Key-Value store with a Time-To-Live (TTL) attribute. For cleanup, rely on lazy deletion (delete on read if expired) coupled with a background asynchronous sweeper (cron job) to reclaim storage space efficiently without blocking the critical read/write path.

**Explanation:** Active sweeping of massive datasets is expensive. Combining passive lazy deletion (checking on access) with low-priority background sweeps ensures fast reads and steady space reclamation.

**Boundary/Misconception:** Using a synchronous trigger or active timer for every single item, which consumes excessive CPU.

**Source:** [`../../../04-hld-projects/pastebin/PROBLEM.md`](../../../04-hld-projects/pastebin/PROBLEM.md)

### Card 13
**Front:** How do you architect a Distributed Object Storage system to handle massive file uploads using multipart upload?

**Answer:** Break large files into smaller chunks (e.g., 5MB). The client uploads parts in parallel directly to blob storage servers (using presigned URLs). A metadata service tracks the completion of all parts and, upon receiving a "complete" signal, stitches them logically into a single file entity.

**Explanation:** Multipart uploads allow parallelization, improving throughput. It also adds resilience, as a network failure requires retrying only a 5MB chunk rather than the entire 10GB file.

**Boundary/Misconception:** Requiring clients to upload a massive file in a single monolithic HTTP request, which often times out or fails mid-transfer.

**Source:** [`../../../04-hld-projects/distributed-object-storage/PROBLEM.md`](../../../04-hld-projects/distributed-object-storage/PROBLEM.md)

### Card 14
**Front:** What are the main challenges in maintaining cross-region replication in a Multi-Region Active-Active database deployment?

**Answer:** Dealing with high WAN latency and conflict resolution. Writes can occur concurrently in multiple regions. Solutions involve asynchronous replication, vector clocks, last-write-wins (LWW) timestamping, or CRDTs to achieve eventual consistency while preserving local read/write availability.

**Explanation:** Synchronous cross-region replication violates availability goals due to the speed of light (WAN latency). Active-Active systems must embrace eventual consistency and provide mechanisms to handle merge conflicts.

**Boundary/Misconception:** Assuming strict ACID consistency can be maintained globally across active-active regions without significant latency penalties.

### Card 15
**Front:** How do you structure a distributed inverted index to enable low-latency Social Post Search?

**Answer:** Shard the inverted index by Document ID (each shard searches its subset and an aggregator merges top results) or by Term (each term maps to a specific shard). Document-based sharding is standard for social search to easily scale write throughput and apply localized ranking features.

**Explanation:** Document-partitioning allows incoming posts to be written to a single shard quickly. A query fans out to all shards in parallel (Scatter-Gather), which is efficient if the number of shards is reasonable.

**Boundary/Misconception:** Storing the entire inverted index on a single node, which cannot scale for massive corpuses or high query volumes.

**Source:** [`../../../04-hld-projects/social-post-search/PROBLEM.md`](../../../04-hld-projects/social-post-search/PROBLEM.md)

### Card 16
**Front:** How does a Kafka Distributed Broker handle partition replication and consumer group offsets?

**Answer:** Partitions are replicated across brokers; one is elected Leader to handle all reads/writes. Followers passively fetch data. Consumer offsets are durably stored in an internal Kafka topic (`__consumer_offsets`), allowing consumers to resume precisely after restarts or rebalancing within their consumer group.

**Explanation:** Storing offsets in Kafka itself (rather than external Zookeeper) reduces dependencies and improves performance. Replication ensures high availability if the leader broker crashes.

**Boundary/Misconception:** Treating Kafka like a traditional message queue where messages are deleted immediately after a single consumer reads them. Kafka retains messages until retention policies expire.

**Source:** [`../../../04-hld-projects/kafka-distributed-broker/PROBLEM.md`](../../../04-hld-projects/kafka-distributed-broker/PROBLEM.md)

### Card 17
**Front:** How do you implement chunking, transcoding, and adaptive bitrate streaming in a Video Streaming platform?

**Answer:** Original videos are uploaded to blob storage and trigger queue events. Transcoding workers pull events, split the video into small chunks (e.g., 5s), and encode them into multiple resolutions/bitrates. A manifest file (HLS/DASH) indexes the chunks, allowing players to dynamically switch streams based on network bandwidth via a CDN.

**Explanation:** Adaptive Bitrate (ABR) streaming ensures smooth playback by seamlessly shifting between low and high-quality chunks based on the client's current internet speed.

**Boundary/Misconception:** Streaming a single monolithic video file directly from an application server without chunking or CDN caching.

### Card 18
**Front:** What pipeline architecture is required to serve real-time personalized Video Recommendations at scale?

**Answer:** Use a lambda or kappa architecture. Stream user interactions via Kafka to real-time processors (Flink) for immediate context updates (e.g., trending). Periodically run batch jobs (Spark) on massive data lakes to train deep learning models. A feature store serves the latest features to an online inference service for low-latency ranking.

**Explanation:** Recommendations require a two-stage approach: candidate generation (retrieving hundreds of relevant items) followed by heavy ML scoring to rank the top 10.

**Boundary/Misconception:** Running a deep learning ranking model synchronously on the entire video catalog for every incoming user request.

### Card 19
**Front:** How do you handle high-throughput event ingestion and real-time aggregations in an Ad Click Aggregator?

**Answer:** Ingest clicks into a distributed log (Kafka) to decouple and buffer bursts. Use a stream processing engine (Flink) for stateful real-time aggregation within time windows. Store the aggregated results in a fast OLAP database (Druid or ClickHouse) capable of serving sub-second slice-and-dice queries.

**Explanation:** Kafka acts as a shock absorber. Stream processing handles the grouping by time and ad ID, converting raw events into aggregated metrics before storing them in an analytical database.

**Boundary/Misconception:** Writing raw click events directly into an OLTP relational database and aggregating them on the fly during reads.

### Card 20
**Front:** What storage engine optimizations are necessary for a Metrics Monitoring system handling high-cardinality time-series data?

**Answer:** Time-Series Databases (TSDBs like Prometheus/InfluxDB) use Log-Structured Merge (LSM) trees or specialized append-only blocks to optimize for heavy write throughput. They group data by metric name and labels, applying robust delta-of-delta and XOR compression (e.g., Gorilla paper) to store timestamps and values compactly.

**Explanation:** Metrics systems are 99% writes. By aggressively compressing sequential timestamps and slowly changing values, TSDBs drastically reduce disk I/O and footprint.

**Boundary/Misconception:** Using a standard relational database with row-based storage, which becomes highly inefficient for storing billions of data points.

**Source:** [`../../../04-hld-projects/metrics-monitoring/PROBLEM.md`](../../../04-hld-projects/metrics-monitoring/PROBLEM.md)

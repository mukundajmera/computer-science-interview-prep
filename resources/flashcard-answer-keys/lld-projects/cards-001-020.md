# LLD Projects - Flashcard Answers (1-20)

This document provides answers, common boundaries, and concept links for the first 20 cards in the LLD projects flashcards deck.

### Card 1
**Front:** In a Parking Lot LLD, what design pattern is typically used to ensure only one instance of the parking lot exists?

**Answer:** The **Singleton** pattern is typically used to ensure only a single, globally accessible instance of the `ParkingLot` coordinates the system state.

**Common Boundary / Misconception:** Using a strict Singleton can make testing difficult due to shared global state; Dependency Injection is often preferred in modern systems.

**Concept Link:** [`../../../02-lld-projects/parking-lot/APPROACH.md`](../../../02-lld-projects/parking-lot/APPROACH.md)

### Card 2
**Front:** How would you model the relationship between a `ParkingTicket` and a `ParkingSpot` in a Parking Lot system?

**Answer:** A `ParkingTicket` usually contains a reference to the `ParkingSpot` (or its ID) it was issued for, establishing a 1-to-1 association during the parking session.

**Common Boundary / Misconception:** Assuming a spot holds the ticket. The ticket tracks the spot; the spot usually only tracks its occupancy status and type, not the transient ticket.

**Concept Link:** [`../../../02-lld-projects/parking-lot/PROBLEM.md`](../../../02-lld-projects/parking-lot/PROBLEM.md)

---

### Card 3
**Front:** In a Parking Lot design, which class is responsible for finding the next available parking spot?

**Answer:** The `ParkingLot` or `Floor` class typically delegates to a spot allocation strategy to find the next available `ParkingSpot` based on the vehicle type.

**Common Boundary / Misconception:** Placing allocation logic inside the `Vehicle` or `ParkingSpot` itself, which violates the Single Responsibility Principle.

**Concept Link:** [`../../../02-lld-projects/parking-lot/PROBLEM.md`](../../../02-lld-projects/parking-lot/PROBLEM.md)

---

### Card 4
**Front:** How does the Strategy pattern apply to calculating parking fees in a Parking Lot LLD?

**Answer:** The **Strategy** pattern allows encapsulating different pricing algorithms (e.g., hourly, flat rate, weekend) and injecting the appropriate one at runtime.

**Common Boundary / Misconception:** Hardcoding fee calculation inside the `Ticket` or `ParkingLot` class using complex if-else statements.

**Concept Link:** [`../../../02-lld-projects/parking-lot/APPROACH.md`](../../../02-lld-projects/parking-lot/APPROACH.md)

### Card 5
**Front:** Which design pattern is best suited for handling the different phases (e.g., Idle, HasMoney, Dispensing) of a Vending Machine?

**Answer:** The **State** pattern is ideal for representing the different behavioral states of a Vending Machine and handling transitions between them.

**Common Boundary / Misconception:** Using a giant switch statement inside the Vending Machine class to handle all actions based on an enum, which becomes unmaintainable.

**Concept Link:** [`../../../02-lld-projects/vending-machine/DESIGN.md`](../../../02-lld-projects/vending-machine/DESIGN.md)

### Card 6
**Front:** In a Vending Machine LLD, what exception should be thrown if a user attempts to select a product before inserting money?

**Answer:** An `IllegalStateException` (or a custom exception like `InsufficientFundsException` / `NoMoneyInsertedException`) should be thrown.

**Common Boundary / Misconception:** Returning a null product or a generic error code instead of explicitly throwing an exception for the invalid state transition.

**Concept Link:** [`../../../02-lld-projects/vending-machine/DESIGN.md`](../../../02-lld-projects/vending-machine/DESIGN.md)

### Card 7
**Front:** How do you ensure thread safety when multiple users attempt to purchase the last remaining item in a Vending Machine concurrently?

**Answer:** By using pessimistic locking (e.g., `synchronized` blocks or `ReentrantLock` in Java) around the inventory decrement operation, or optimistic locking (e.g., compare-and-swap) at the database layer.

**Common Boundary / Misconception:** Assuming standard `HashMap` or unsynchronized data structures are thread-safe, leading to race conditions and overselling.

**Concept Link:** [`../../../02-lld-projects/vending-machine/APPROACH.md`](../../../02-lld-projects/vending-machine/APPROACH.md)

### Card 8
**Front:** What is the role of an `Inventory` class in the Vending Machine system design?

**Answer:** The `Inventory` class manages the quantity and placement of items, abstracting stock management away from the core Vending Machine state logic.

**Common Boundary / Misconception:** Conflating inventory tracking with the physical dispensing logic or state machine transitions.

**Concept Link:** [`../../../02-lld-projects/vending-machine/APPROACH.md`](../../../02-lld-projects/vending-machine/APPROACH.md)

### Card 9
**Front:** In a Library Management system, what is the difference between a `Book` and a `BookItem`?

**Answer:** A `Book` represents the abstract concept (e.g., title, author, ISBN), while a `BookItem` represents a physical copy with a specific barcode and location.

**Common Boundary / Misconception:** Treating all copies of a book as the same entity, which makes it impossible to track physical wear, specific barcodes, or individual loans.

**Concept Link:** [`../../../02-lld-projects/library-management/PROBLEM.md`](../../../02-lld-projects/library-management/PROBLEM.md)

---

### Card 10
**Front:** How would you model the relationship between a `Member` and a `LibraryCard`?

**Answer:** A `Member` has a 1-to-1 composition or aggregation relationship with a `LibraryCard`, which serves as the authorization token for borrowing.

**Common Boundary / Misconception:** Making `LibraryCard` a subclass of `Member`, confusing identity with authorization credentials.

**Concept Link:** [`../../../02-lld-projects/library-management/PROBLEM.md`](../../../02-lld-projects/library-management/PROBLEM.md)

### Card 11
**Front:** Which design pattern can be used to notify members when a reserved book becomes available in the library?

**Answer:** The **Observer** pattern (or Publisher-Subscriber) can be used to notify all users on a waitlist when the reserved book item is returned.

**Common Boundary / Misconception:** Polling the library system repeatedly, which wastes resources and adds latency.

**Concept Link:** [`../../../02-lld-projects/library-management/DESIGN.md`](../../../02-lld-projects/library-management/DESIGN.md)

### Card 12
**Front:** How do you handle the state transition of a `BookItem` when it is checked out, returned, or lost?

**Answer:** Using a state machine or the **State** pattern to transition the `BookItem` status between Available, Loaned, Lost, or Reserved.

**Common Boundary / Misconception:** Allowing manual string updates to the state, leading to inconsistent transitions (e.g., returning a book that was never loaned).

**Concept Link:** [`../../../02-lld-projects/library-management/APPROACH.md`](../../../02-lld-projects/library-management/APPROACH.md)

### Card 13
**Front:** In an LRU Cache LLD, what combination of data structures is used to achieve O(1) time complexity for `get` and `put` operations?

**Answer:** A **HashMap** (for O(1) lookups) combined with a **Doubly Linked List** (for O(1) eviction and reordering).

**Common Boundary / Misconception:** Using a single Array or Singly Linked List, which degrades eviction or lookup to O(N).

**Concept Link:** [`../../../02-lld-projects/lru-cache/APPROACH.md`](../../../02-lld-projects/lru-cache/APPROACH.md)

---

### Card 14
**Front:** Why is a Doubly Linked List preferred over a Singly Linked List in the implementation of an LRU Cache?

**Answer:** A Doubly Linked List allows O(1) removal of an arbitrary node because it holds pointers to both its predecessor and successor.

**Common Boundary / Misconception:** Believing a Singly Linked List is sufficient; finding the predecessor in a singly linked list requires O(N) traversal.

**Concept Link:** [`../../../02-lld-projects/lru-cache/DESIGN.md`](../../../02-lld-projects/lru-cache/DESIGN.md)

---

### Card 15
**Front:** In an LRU Cache design, what happens when the cache reaches its maximum capacity and a new item is added?

**Answer:** The least recently used item (typically at the tail of the linked list) is evicted and removed from the hash map before the new item is inserted at the head.

**Common Boundary / Misconception:** Evicting random items or failing to update the hash map, causing memory leaks and stale reads.

**Concept Link:** [`../../../02-lld-projects/lru-cache/PROBLEM.md`](../../../02-lld-projects/lru-cache/PROBLEM.md)

---

### Card 16
**Front:** How would you make an LRU Cache thread-safe in a multi-threaded environment?

**Answer:** By using thread-safe data structures like `ConcurrentHashMap` combined with explicit locks (e.g., `ReentrantLock` or `ReadWriteLock`) around list mutations.

**Common Boundary / Misconception:** Simply wrapping the entire cache with `synchronized`, which serializes all reads and writes, severely bottlenecking performance.

**Concept Link:** [`../../../02-lld-projects/lru-cache/APPROACH.md`](../../../02-lld-projects/lru-cache/APPROACH.md)

---

### Card 17
**Front:** In a Message Queue LLD, what is the difference between the Point-to-Point and Publisher-Subscriber messaging models?

**Answer:** In Point-to-Point, a message is consumed by exactly one receiver. In Pub/Sub, a message is broadcast to all active subscribers of a topic.

**Common Boundary / Misconception:** Confusing consumer groups in modern brokers (which act like point-to-point within the group) with true fan-out pub/sub.

**Concept Link:** [`../../../02-lld-projects/message-queue/PROBLEM.md`](../../../02-lld-projects/message-queue/PROBLEM.md)

---

### Card 18
**Front:** How do you implement the 'at-least-once' delivery semantic in a custom Message Queue design?

**Answer:** By requiring explicit consumer acknowledgments (ACKs); if an ACK isn't received within a timeout, the message is re-queued or redelivered.

**Common Boundary / Misconception:** Assuming network delivery equals successful processing, leading to message loss if the consumer crashes before committing.

**Concept Link:** [`../../../02-lld-projects/message-queue/DESIGN.md`](../../../02-lld-projects/message-queue/DESIGN.md)

---

### Card 19
**Front:** What is the role of a `Topic` and a `Subscription` in a Pub/Sub Message Queue?

**Answer:** A `Topic` acts as a logical channel for messages. A `Subscription` tracks the specific reading offset or message queue for a consumer group listening to that topic.

**Common Boundary / Misconception:** Hardcoding subscribers directly into the topic without an intermediate subscription entity to track individual progress.

**Concept Link:** [`../../../02-lld-projects/message-queue/APPROACH.md`](../../../02-lld-projects/message-queue/APPROACH.md)

---

### Card 20
**Front:** How would you handle message ordering guarantees within a specific partition of a Message Queue?

**Answer:** By ensuring all messages with the same routing key are assigned to the same partition, and that partition is processed by a single consumer thread.

**Common Boundary / Misconception:** Attempting to guarantee global ordering across all partitions, which severely limits scalability and concurrency.

**Concept Link:** [`../../../02-lld-projects/message-queue/DESIGN.md`](../../../02-lld-projects/message-queue/DESIGN.md)

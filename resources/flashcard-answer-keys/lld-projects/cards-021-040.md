### Card 21
**Front:** In a Movie Ticket Booking system, how do you handle concurrency when two users try to book the same seat simultaneously?

**Answer:** By utilizing pessimistic locking (e.g., database `SELECT ... FOR UPDATE`) or optimistic locking with a version number to ensure only one transaction successfully claims the seat.

**Explanation:** Concurrency control is critical to prevent double-booking. When multiple requests target the same seat, locking mechanisms ensure that the first transaction locks the record and subsequent ones either wait or fail.

**Boundary/Misconception:** Relying purely on application-level logic without database locks, which fails in distributed environments with multiple instances handling requests.

### Card 22
**Front:** What is the difference between a `Show` and a `Movie` in the context of a Ticket Booking LLD?

**Answer:** A `Movie` represents the metadata (title, genre, duration), while a `Show` (or `Showtime`) represents a specific instance of a movie playing at a given time and screen.

**Explanation:** Separating the metadata from the physical screening allows the system to easily schedule the same movie across multiple times and screens without duplicating movie details.

**Boundary/Misconception:** Combining both into a single entity, which makes it difficult to manage schedules, track multiple showings, and manage seat availability per screening.

**Answer:** The **SCAN** (Elevator Algorithm) or **LOOK** algorithm is typically used.

**Explanation:** These algorithms dictate that the elevator continues moving in its current direction, servicing all requests in that path until there are no more, before reversing direction, optimizing throughput.

### Card 33
**Front:** In a Rate Limiter LLD, how does the Token Bucket algorithm differ from the Leaky Bucket algorithm?

**Answer:** The Token Bucket algorithm adds tokens at a fixed rate and allows bursts up to the bucket's capacity, whereas Leaky Bucket processes requests at a strict, constant rate.

**Explanation:** Token Bucket is memory-efficient and ideal for APIs that tolerate occasional spikes, while Leaky Bucket (using a queue) smooths out traffic to a strict maximum outflow.

**Boundary/Misconception:** Confusing the two algorithms or assuming Leaky Bucket handles bursts efficiently (it inherently forces a constant outflow, queuing or dropping excess).

### Card 34
**Front:** What is the primary advantage of using a Sliding Window Log over a Fixed Window Counter in a Rate Limiter design?

**Answer:** The Sliding Window Log prevents the 'edge burst' problem inherent in the Fixed Window Counter by evaluating requests dynamically against the precise time boundary.

**Explanation:** A Fixed Window can allow double the intended rate if bursts happen across the reset boundary. The Sliding Window Log tracks exact timestamps to provide an accurate rolling count.

**Boundary/Misconception:** Assuming Sliding Window Log is as memory-efficient as Fixed Window; logging every timestamp consumes significantly more memory and processing power.

**Source:** [`../../../02-lld-projects/rate-limiter/APPROACH.md`](../../../02-lld-projects/rate-limiter/APPROACH.md)

### Card 35
**Front:** How do you store and retrieve the request counts per user efficiently in a distributed Rate Limiter?

**Answer:** By using a fast, in-memory datastore like Redis to store counters, utilizing sorted sets for sliding windows or atomic `INCR` with TTL for fixed windows.

**Explanation:** Redis provides the high throughput and low latency necessary for rate-limiting operations, along with atomic operations to prevent race conditions in distributed environments.

**Boundary/Misconception:** Storing rate limit counters in a traditional relational database (e.g., PostgreSQL/MySQL), which introduces high latency and locking contention on every request.

# Distributed Tracing System - Interview Follow-Ups

After establishing the high-level design, interviewers will often probe deeper into specific areas of the architecture. Here are common follow-up questions and expected answers.

## 1. Handling Missing Spans and Stragglers
**Question:** In Tail-Based Sampling, you hold traces in memory for 30 seconds. What happens if a service crashes or network lag delays a span, and it arrives 45 seconds later, after the sampling decision was made?

**Answer:**
This is inevitable in distributed systems. We have two options:
1. **Drop it (Simplicity):** Tracing is not a financial ledger. If a span arrives after the window has closed and the trace was discarded, we simply drop the orphan span. 
2. **Re-evaluate (Complexity):** If it arrives late but the original trace *was* sampled and saved, we can append the late span directly to the storage layer (Cassandra supports updates/inserts equally well). If the original trace was dropped, we can force-sample the late span just in case it contains an error, though it will lack context.

## 2. Dynamic Sampling Rates
**Question:** A 1% uniform sampling rate means we store too much data during peak hours, and too little during off-peak. How can we make this smarter?

**Answer:**
We can implement an Adaptive/Dynamic Sampling strategy. 
- The collectors or stream processors can monitor the current throughput.
- We maintain a target write rate to the database (e.g., 50,000 spans/sec max).
- If traffic spikes by 10x, the system dynamically adjusts the baseline probabilistic sampling rate from 1% down to 0.1% to protect the storage layer, while still keeping 100% of error traces.

## 3. Clock Skew Between Services
**Question:** Spans are generated by thousands of independent servers. What happens if Server A's clock is 50ms ahead of Server B's clock? A child span might appear to start *before* its parent.

**Answer:**
Clock skew is a major problem in distributed tracing.
- **Client-side:** We cannot rely on system clocks (NTP drift is real). 
- **Backend Fix:** The UI or Query API must reconstruct the trace using the parent-child relationships and observed durations, rather than absolute timestamps. If Server A calls Server B, the start time of B's span must logically be adjusted to fall within the start/end boundaries of A's span, regardless of B's reported absolute timestamp.

## 4. Cold Storage and Analytics
**Question:** Security wants to run an audit on all traces from 6 months ago. Our Cassandra cluster only retains data for 7 days. How do we support this?

**Answer:**
- Before data is TTL'd (Time-To-Live) out of Cassandra, we run a daily batch job (e.g., Spark).
- This job exports the older traces, compresses them heavily (e.g., Parquet format), and writes them to a Data Lake (like AWS S3).
- For audits, we can use a query engine like AWS Athena or Presto to query the S3 bucket directly, accepting higher latency for these rare analytical queries.

## 5. Security & PII Redaction
**Question:** How do you ensure sensitive data (PII, credit card numbers, passwords) isn't accidentally logged in a trace and exposed in the UI?

**Answer:**
Redaction must happen as early as possible.
1. **SDK Level:** Configure the tracing client to drop specific headers (e.g., `Authorization`) or sanitize specific payload fields before leaving the application boundary.
2. **Collector Level:** Implement middleware in the Collector to regex-match and mask common patterns (like SSNs or 16-digit CC numbers) across all incoming spans before they are written to the message queue.

# Common Pitfalls

- **Ignoring Application Overhead:** Assuming apps can just send HTTP requests to a central collector for every span. This will block application threads and cause cascading failures. Local sidecars or UDP agents are necessary.
- **Misunderstanding Tail-Based Sampling:** Thinking tail-based sampling can be done immutably row-by-row. It requires buffering all spans for a given `trace_id` for a window of time before making a keep/drop decision.
- **Elasticsearch Defaulting:** While ES is popular (e.g., Jaeger initially), for massive scale tracing, columnar databases (ClickHouse) are far superior due to high cardinality tags and write-heavy workloads.
- **Forgetting Clock Skew:** Assuming timestamps from different servers are perfectly aligned when assembling the DAG.
- **Relying Solely on Head-Based Sampling for Error Diagnostics:** Making a random 1% keep/drop decision at the edge via the `traceparent` header saves bandwidth but silently drops rare errors and p99 latency spikes (>1s). Pair lightweight head sampling with stateful tail-based sampling in Ingestion Workers when capturing anomalous traces is required.
- **Writing Spans Directly from Collectors to ClickHouse Without a Buffer:** Sending 1M spans/sec (~600 MB/s) directly into storage causes immediate telemetry loss and backpressure whenever ClickHouse degrades or undergoes compaction. Decouple ingestion with a durable Kafka buffer so workers can pause and drain the backlog without dropping spans.
- **Partitioning Kafka Randomly Instead of by `trace_id`:** Tail-based sampling requires evaluating all spans of a trace together inside a single worker's 30-second memory buffer. If spans for the same `trace_id` land on different Kafka partitions and workers, traces fragment and tail-sampling decisions become incomplete.
- **Omitting Deduplication for At-Least-Once Kafka Replays:** Re-consuming Kafka partitions after a worker restart or storage timeout writes duplicate spans into ClickHouse. Deduplicate on `(trace_id, span_id)` using ClickHouse `ReplacingMergeTree` (or query-time deduplication) rather than slowing down the 99.9% write path with synchronous lookups.
- **Ignoring In-Memory Tail-Sampling Loss During Worker Crashes and Rebalances:** Holding 30 seconds of full-volume spans in worker RAM means a worker crash or Kafka consumer-group rebalance drops in-flight buffers and fragments active traces. Bound memory per worker, monitor rebalance rates, and document the brief crash-window trade-off in the availability contract.

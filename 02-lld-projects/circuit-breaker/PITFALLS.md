# Common Pitfalls

## 1. Penalizing the Backend for Self-Rejections (Failure Trace)

A classic mistake is to count the `CircuitBreakerOpenException` (thrown when the circuit is open) as a backend failure. If the circuit breaker is open, it rejects calls immediately. If these rejections are logged as failures, the failure rate will stay high, and the circuit will never close, even after the `HALF_OPEN` test calls succeed.

**Failure Trace:**
1. Failure rate > 50%. State -> `OPEN`.
2. Client sends 100 requests. CircuitBreaker instantly throws 100 `CircuitBreakerOpenException`s.
3. If these are caught by a global `try/catch` in the execute block and routed to `onError()`, the failure rate remains 100%.
4. State transitions to `HALF_OPEN`. The next valid call succeeds, but the metrics window still shows > 50% failures because of the stored exceptions. State -> `OPEN`. The circuit is deadlocked.

**Solution:** Ensure that the fast-fail response generated by the circuit breaker itself is explicitly excluded from being recorded as a backend failure (e.g., `if (!(e instanceof CircuitBreakerOpenException)) { onError(duration); }`).

## 2. Memory Leaks in Time-Based Windows

When implementing a time-based sliding window, developers sometimes use a dynamically growing list or map to store events and periodically clean them up in a background thread. If the background thread stalls or the cleanup logic is flawed, this can lead to memory leaks.

**Solution:** Use a fixed-size circular array of buckets. Overwrite old buckets as time advances, rather than dynamically allocating and deallocating memory.

## 3. Coarse-Grained Locking Bottlenecks

Using `synchronized` on the main `execute` method or the entire metric aggregator ensures thread safety but completely serializes all requests passing through the circuit breaker. This turns the circuit breaker into a massive performance bottleneck.

**Solution:** Use fine-grained locking or lock-free data structures (like `AtomicReference` and `AtomicInteger` in Java) to allow concurrent execution and metric updates.

## 4. Half-Open Stampedes

When the circuit transitions from `OPEN` to `HALF_OPEN`, it should only allow a limited number of test calls (e.g., 1 or 2). If the implementation blindly allows all incoming requests until a failure occurs, a sudden spike in traffic could overwhelm the recovering backend.

**Solution:** Use an atomic counter (`halfOpenCalls.incrementAndGet()`) to strictly limit the number of permitted calls in the `HALF_OPEN` state.

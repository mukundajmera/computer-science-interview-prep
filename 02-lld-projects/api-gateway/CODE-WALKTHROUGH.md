# Code Walkthrough: API Gateway

## Version Delta Table

| Version | Features | Complexity |
|---|---|---|
| `v1-basic` | Core routing, simple POJO models, basic pre-filters (AuthFilter) | O(R) time where R is route count. Space O(1) beyond routes |
| `v2-extended` | Adds post-filters (LoggingFilter), simple sliding window RateLimiting | O(R + F) time. Space O(C * N) for rate limit timestamps |
| `v3-optimized` | Circuit Breaker integration, thread safety (locks, concurrent collections) | O(R + F) time. Concurrent overhead limits contention |

## Interview Pacing (45-minutes)
- **0-10m:** Core POJOs (Request/Response) and Basic Routing (`v1-basic`).
- **10-25m:** Filter Chain (pre/post) and basic stateful filters (`v2-extended`).
- **25-45m:** Circuit Breaker, thread-safety, and invariant protection (`v3-optimized`).

## v1 Basic
The `v1-basic` implementation focuses on the core mechanics of an API Gateway: defining the request/response models, setting up basic routing, and introducing a simple pre-filter pattern.
- `ApiGateway.Request` and `ApiGateway.Response` are simple POJOs representing HTTP concepts.
- The entry API `handle(Request)` processes routing.
- The `Filter` interface defines a single `filter(Request)` method. The `AuthFilter` checks for an `Authorization` header and returns a 401 response if missing, short-circuiting the request.
- Routing is handled by comparing the request path's prefix to registered `Route` objects.
- Dispatching maps the target string to a lambda function representing the backend.

## v2 Extended
The `v2-extended` implementation enhances the filter chain and adds more complex filters.
- The `Filter` interface is expanded to include `preFilter` and `postFilter` methods.
- The `handle` method applies pre-filters in order. If a pre-filter short-circuits or if backend processing finishes, `applyPostFilters` applies the post-filters in reverse order.
- `RateLimitFilter` implements a simple sliding-window rate limiter per `Client-ID`. It cleans up old timestamps and checks against a maximum request limit.
- `LoggingFilter` adds start time to request attributes in the pre-filter and logs the total duration and status code in the post-filter.

## v3 Optimized
The `v3-optimized` implementation introduces concurrency controls and the Circuit Breaker pattern for resiliency.
- **Correctness Invariants**: Rate limit time window bounds are exactly enforced. Circuit breaker state integrity is preserved using thread-safe primitives.
- `ReentrantLock` and concurrent collections (`ConcurrentHashMap`, `CopyOnWriteArrayList`) are used to ensure thread safety across rate limiters and gateway state.
- `CircuitBreaker` maintains state (`CLOSED`, `OPEN`, `HALF_OPEN`) using `AtomicReference` and `AtomicInteger`.
- The routing logic checks the circuit breaker state before dispatching. If `OPEN`, it fails fast with a 503.
- After dispatching, the gateway correctly records successes or failures (exceptions or 5xx responses) on the circuit breaker.
- The implementation specifically ensures that failures generated by internal gateway filters (like 429 Too Many Requests) do not trigger or affect the backend's circuit breaker.

# Problem Statement: API Gateway

Design and implement a low-level API Gateway that proxies client requests to backend services. 
The system should demonstrate core API Gateway patterns, including routing, filtering, rate limiting, and fault tolerance via circuit breakers.

## Core Requirements

1. **Routing and Dispatching**
   - The gateway must parse incoming requests and route them to the correct backend service based on URL prefixes.
   - It should gracefully handle routes that are not found (e.g., return HTTP 404), invalid routes, and downstream cancellation.

2. **Filter Chain (Pre-filters and Post-filters)**
   - The system must support an extensible filter chain to process requests before dispatching them to the backend, and to process responses before returning them to the client.
   - **Authentication Pre-filter:** A filter that rejects requests missing an authorization token (returns HTTP 401). Authentication explicitly precedes protected routing.
   - **Rate Limiting Pre-filter:** A filter that restricts the number of requests a single client can make within a time window (returns HTTP 429).
   - **Logging/Metrics Post-filter:** A filter that logs request metadata, response status codes, and the duration of the request.

3. **Resiliency and Advanced Features**
   - **Circuit Breaker:** The gateway must integrate a Circuit Breaker pattern to protect failing backend services. If a backend service returns a high rate of errors (e.g., HTTP 5xx) or times out, the circuit breaker should trip (open) and fail fast, immediately returning an error (e.g., HTTP 503). Fast-fail responses generated by the gateway's own filters (e.g., HTTP 429) explicitly do not affect the circuit breaker state.
   - **Deadline Propagation & Retries:** Implement deadline propagation and define duplicate retry eligibility for downstream calls.
   - **Request Validation:** Enforce a bounded request body size.

4. **Concurrency**
   - The system should be thread-safe, supporting multiple concurrent requests being processed and routed simultaneously.
   - Rate limiters and circuit breakers must function correctly under concurrent load without data races.

## Testing & Fixtures
- Use fake request/response fixtures to show exact filter order, short-circuit rejection, and one downstream call.
- Deadline propagation, duplicate retry eligibility, bounded request body, invalid route, and downstream cancellation must be tested without live servers or generic SSRF-safe claims.
- Version-specific APIs and deterministic fixture inputs/expected outputs must be fixed before implementation.

## Out of Scope

- Distributed state (e.g., Redis-backed rate limiting). The scope is limited to a single-node API Gateway using in-memory state.
- Dynamic route registration at runtime (routes can be registered at startup).
- Request/response payload transformation (beyond simple headers/status codes).
- No production or security promise is inferred.

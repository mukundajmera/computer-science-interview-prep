# Pitfalls in Ad Click Aggregator

## Supported Versions
- **v1-basic:** A single-node in-memory event aggregator with tumbling windows and simple deduplication.
- **v2-extended:** Introduces deduplication caches, a flush policy for handling late events, and fraud rules for basic filtering.
- **v3-optimized:** A distributed, sharded state store with compaction scheduling, snapshot replay, and robust watermark management for high-throughput stream processing.

## 1. Conflating Processing Time with Event Time
A fundamental error in building aggregation systems is relying on `System.currentTimeMillis()` at the moment the server processes the event, rather than parsing the timestamp generated by the client device.
- **The Pitfall:** If a processing node crashes or the message queue backs up, a massive batch of older events might be processed simultaneously. If using processing time, all these historical events will be incorrectly attributed to the current minute's window, destroying the accuracy of the time-series data and resulting in wildly inaccurate analytics and billing spikes.
- **The Solution:** Always extract and utilize the event time embedded in the payload. Implement robust watermarking to handle the delayed arrival of these events, allowing the system to retroactively update historical windows if necessary, or gracefully reject them if they are too old. Window-boundary, late-event and out-of-order timestamp examples state processing-time/event-time policy; empty input and invalid event payloads fail predictably. For instance, an event arriving exactly at a window boundary (e.g., `10:01:00.000`) is bucketed strictly into the `10:01-10:02` window based on its event-time. Out-of-order events (e.g., event-time `10:01:30` arriving at processing-time `10:04:00`) are accepted if within the watermark. Late events (e.g., same event arriving at `10:08:00`) exceeding the processing-time watermark are rejected. Finally, empty input and invalid event payloads are blocked predictably during initial ingestion.

## 2. Inadequate State Management leading to OOM
Stream processing involves holding the state of active windows in memory. 
- **The Pitfall:** If the system tracks millions of unique `ad_id`s, and events can be up to an hour late, the number of active `WindowKey` objects in the `ConcurrentHashMap` grows astronomically. Without aggressive eviction, the JVM heap will eventually fill up, leading to prolonged Garbage Collection pauses (Stop-The-World events) and ultimately an `OutOfMemoryError`, crashing the node.
- **The Solution:** Implement strict window closing and state eviction policies. Once a window is flushed to the database, it must be completely removed from memory. For massive cardinality dimensions, avoid holding the entire state in RAM. Utilize off-heap memory or an embedded state backend like RocksDB, which spills to disk efficiently while keeping a small working set in memory.

## 3. The Deduplication Bottleneck
Clients will retry requests, leading to duplicate events. Deduplication is required, but it is incredibly resource-intensive.
- **The Pitfall:** Storing every single `event_id` in a relational database and doing a `SELECT` before every insert will completely cripple the throughput of the system. The network I/O and database locks will become the primary bottleneck, preventing the system from handling thousands of events per second.
- **The Solution:** Utilize probabilistic data structures. A Bloom filter can hold millions of IDs in a few megabytes of memory and can instantly confirm if an event is definitively *new*. Only if the Bloom filter says it *might* have seen the event do you fall back to checking a distributed cache like Redis. By strictly checking this cache before incrementing, duplicate event IDs affect billing aggregates exactly once; probabilistic filters only accelerate an exact deduplication check. Ensure Redis keys have a strict TTL to prevent memory exhaustion.

## 4. The Thundering Herd Problem during Checkpointing
To ensure fault tolerance, the in-memory state must be periodically saved (checkpointed).
- **The Pitfall:** If multiple processing nodes are configured with the exact same checkpointing interval (e.g., every 60 seconds), they will all attempt to serialize and flush their state to the database at the exact same millisecond. This creates a massive spike in network traffic and database write load, leading to timeouts, degraded performance, and potential cascading failures.
- **The Solution:** Introduce jitter into the checkpointing schedule. Each node should calculate its checkpoint interval with a randomized offset (e.g., 60 seconds +/- 15 seconds). This spreads the write load evenly across the time window, preventing spikes and ensuring stable database performance.
